# Adaptador de Design System → Core TWCSS de ELAN-SK

## Qué hace esta skill

Toma un diseño de cualquier origen (imagen, capturas, Figma, HTML/CSS suelto, documento) y lo traduce al core CSS propio del usuario, manteniendo su arquitectura de tokens (`assets/core/`), lo instala en el proyecto correspondiente, y entrega una prueba visual real y funcional. También actúa como guardrail de estilo permanente: cualquier componente que se cree después en un proyecto con este core debe seguir sus reglas.

Antes de escribir código, leer siempre `references/philosophy.md` (reglas condensadas). Los demás archivos de `references/` se consultan según la etapa del flujo.

Para las decisiones de diseño que no son puramente mecánicas (contraste, anti-patrones visuales, validación final de calidad), esta skill se apoya en el skill `impeccable` cuando está instalado en el proyecto: en vez de decidir esos aspectos por sí sola, lee sus reglas generales como criterio adicional y ejecuta sus comandos (`audit`, `critique`) en los puntos del flujo detallados abajo.

## Flujo de trabajo

### 1. Identificar el input
Puede ser imagen, Figma (si el usuario tiene el conector, úsalo directo), HTML/CSS, o un documento de texto con tokens. Extraer: paleta de colores, tipografías, jerarquía de tamaños de texto, estilos de botones/formularios si están visibles.

### 2. Identificar el proyecto destino
Si no es evidente por el contexto de la conversación o archivos ya vistos, preguntar: ¿WordPress, Drupal, Wagtail, React, Next.js, Tauri, u otro? Si ya se detectó antes en la conversación (ej. por `package.json`, `Cargo.toml`, estructura de carpetas vista), no volver a preguntar.
- WordPress → leer `references/frameworks/wordpress.md` (usa `assets/core/`, con plugins JS)
- React / Vite SPA / Next.js / Tauri → leer `references/frameworks/js-frameworks.md` — **modelo unificado**: usar siempre `assets/core/` (con plugins JS) por defecto, igual que WordPress; `assets/core-simple/` es solo un fallback para casos excepcionales (ver esa guía).
- Otro CMS → sección final de `references/frameworks/js-frameworks.md` (preguntas a hacer)
- **Elementor** (además del stack de código, cuando el usuario pide que los mismos tokens estén disponibles nativamente en el Design System del propio Elementor para edición visual libre) → leer `references/frameworks/elementor.md`. No es un destino alternativo al de WordPress — se instala el core normal según `wordpress.md` Y, aparte, se replican los tokens a Elementor siguiendo esa guía.

### 3. Mapear la paleta a los roles fijos del core
Seguir `references/color-mapping.md`. Nunca inventar roles nuevos sin preguntar antes; el objetivo es encajar en los 9 colores + 3 fondos + 3 mensajes existentes.

### 4. Mapear tipografía
3 familias semánticas (`font-serif`=títulos, `font-sans`=texto/UI, `font-mono`=código/detalle) + escala jerárquica (`text-h1...text-small`) recalculada con `clamp()` si los tamaños objetivo cambian (calculadora: https://elan-sk.github.io/calculadora-clamp-css/). Si hay fuentes nuevas de Google Fonts, importarlas según la guía del framework correspondiente.

Si ya existe una página de test (`references/test-page.md`), actualizar ahí mismo el NOMBRE de fuente que se muestra como texto en la sección "Fonts Families" (ej. `<p class="font-serif">Crimson Pro</p>`) — es texto literal, no se actualiza solo al cambiar la variable CSS, y si se olvida la página de test miente sobre qué fuente está aplicada.

### 5. Instalar / actualizar el core en el proyecto
- Si el proyecto no tiene el core: copiar `assets/core/` completo a la ruta que indique la guía del framework.
- Si ya lo tiene: NO sobreescribir toda la carpeta — editar solo `plugins/variables.js`, `settings/_fonts.css`, y (si aplica) `settings/_typography.css`/`settings/_containers.css`.
- Regenerar el safelist si el framework lo requiere (ver guía específica).
- Configurar (o crear si no existe) `.vscode/settings.json` **local al proyecto** con `"files.associations": { "*.css": "tailwindcss" }`, para que VSCode reconozca `@apply`/`@tailwind`/`@theme` en todos los `.css` del repo y no marque falsos "Unknown at rule". Si el archivo ya tiene otras claves en `files.associations`, fusionar en vez de sobreescribir.

### 6. Generar la prueba visual
Seguir `references/test-page.md`. Nunca CSS adicional — siempre una plantilla/componente real del proyecto con las 4 secciones (Colors, Typography, Text Reset, Buttons) usando las clases reales del core.

Si hay Chrome DevTools MCP disponible, cargar la página de prueba en el navegador y revisar (no solo confiar en que el build compiló) que los botones se vean bien sobre TODOS los fondos, incluyendo los que comparten color de marca con el propio botón (ej. `.btn-primary` dentro de una sección `.bg-primary`) — ver `references/philosophy.md §11` para los bugs típicos que no rompen el build pero sí el render (colisión con CSS sin capa del theme padre en WordPress, texto/borde invisible por mal contraste contextual).

Si el skill `impeccable` está instalado en el proyecto, correr `/impeccable audit <ruta-de-la-página-de-prueba>` sobre la página recién generada, antes de pasar al paso 7. Tratar sus hallazgos (contraste, accesibilidad, anti-patrones) como parte de esta misma revisión — corregirlos ahí, no reportarlos como pendientes al usuario.

### 7. Generar `design.md` (documento de referencia de estilo)
Además de la prueba visual (paso 6), producir un `design.md` en la raíz del proyecto (o del tema, si es un CMS con temas) que consolide las reglas de estilo del diseño importado — pensado para consultarse antes de crear cualquier componente nuevo, no solo en esta importación inicial.

Contenido mínimo:
- **Fuente de verdad visual**: link al Figma/imagen de origen (nodo específico si aplica).
- **Regla de forma**: cómo trata el diseño REAL las esquinas (rectas, redondeadas, mixto) — nunca asumir por convención genérica de Tailwind (`rounded-lg` "porque sí"). Documentar también las excepciones puntuales (círculos decorativos, avatares, chips/pills) si el diseño las usa.
- **Color**: tabla de roles ya mapeados en el paso 3 (no repetir hex sueltos, referenciar `variables.js`/equivalente).
- **Tipografía**: escala del paso 4 con su uso (h1…h6, large, button, base, small/eyebrow).
- **Botones**: qué clases/variantes ya existen (`.btn-primary`, etc.) y cuándo usar cada una.
- **Containers/breakpoints** si el core los define.
- **Checklist** corto para antes de crear un componente nuevo (4-6 líneas: ¿forma correcta?, ¿reusa roles de color?, ¿reusa botones/utilities existentes?, ¿se revisó el diseño real ante la duda?).

Si al comparar el diseño real contra el core/componentes ya existentes en el proyecto aparece una discrepancia (ej. el core define un radio para "cards de contenido" pero el diseño real no redondea ninguna card), **documentarla explícitamente en `design.md` como pendiente**, sin corregir el código existente por cuenta propia — preguntar antes si además de documentar hay que corregir los componentes que ya violan la regla. Caso real, CAFEXPORT 2026-07-25: `_borders.css` etiquetaba una escala de radios para botones/cards de contenido, y 4 componentes ya la usaban, pero el Figma real no llevaba ningún `border-radius` salvo círculos decorativos de fondo y avatares — se documentó la discrepancia sin tocar el código existente, a pedido explícito del usuario.

Si `impeccable` está instalado, apoyarse en sus reglas generales (forma, jerarquía, anti-patrones) como criterio adicional al redactar las reglas de `design.md` — en particular para no codificar como "regla del proyecto" un patrón que esa skill ya consideraría anti-patrón (radios inconsistentes, cards-dentro-de-cards, exceso de sombra/decoración). No hace falta correr un comando de `impeccable` sobre el propio `.md` (no es una página renderizada); el apoyo acá es de criterio, igual que en el guardrail permanente de más abajo.

### 8. Confirmar con el usuario
Mostrar qué se mapeó (tabla color original → rol asignado, fuentes asignadas), dónde quedaron los archivos y el `design.md` generado, antes o junto con presentar la prueba visual. Si hubo algún color/rol que no encajó limpio, decirlo explícitamente en vez de forzarlo en silencio.

## Guardrail permanente (no solo al importar diseños)

Cuando se pida crear/editar cualquier botón, card, formulario, sección o componente en un proyecto que ya use este core:
- **Regla estricta, sin excepción**: si el proyecto tiene un `design.md` (generado en el paso 7), leerlo primero — SIEMPRE, no solo al crear un componente desde cero. Aplica igual cuando el plan es reutilizar un átomo/clase YA EXISTENTE en el core (`.chip`, `.badge`, cualquier clase de `atoms/`) para un uso nuevo: que la clase ya exista en el codebase no la exime de chequearse contra `design.md` — el atom puede ser anterior a la regla actual (ej. predatar la auditoría de esquinas rectas) o estar pensado para un contexto distinto (ej. fondo oscuro) del que se le quiere dar ahora. Verificar SIEMPRE, no asumir por "ya está en el core". Caso real, CAFEXPORT 2026-08-08: se reusó `.chip` (pill `rounded-full`, pensado para fondo oscuro tipo hero) como filtro de categorías sobre fondo claro, sin releer `design.md` antes — que ya documentaba explícitamente "esquinas rectas por defecto, redondeado solo si es un círculo real". El usuario lo marcó como error directo ("para qué hacemos el design.md si no lo vas a usar"); se corrigió reemplazando el chip por tabs de texto plano. Es la versión ya adaptada de este `philosophy.md` a los roles/tokens/forma reales de ESE proyecto, y tiene prioridad sobre asumir por analogía con otro componente del mismo repo o por "ya existe en el core, debe estar bien".
- Al terminar cada componente (o tanda de componentes) de una sesión de trabajo iterativa, actualizar `design.md` con lo que ese componente haya confirmado o agregado (nueva variante de botón, patrón de color, regla de forma, discrepancia diseño-real vs. core, etc.) — no esperar a que el usuario lo pida aparte en cada componente, ni acumular los cambios para el final de la sesión.
- **No copiar detalles visuales de un componente parecido sin verificarlos contra el boceto/imagen actual**: alineación de texto, esquinas redondeadas o no, espaciados — la similitud estructural entre dos componentes (ej. dos banners imagen+texto) no autoriza copiar un detalle del anterior que el boceto de este no muestra. Caso real, CAFEXPORT 2026-08-05: al construir `banner-50-50` por analogía con `history-banner`/`purpose-banner` se copió `rounded-2xl` en la imagen (el boceto no la mostraba redondeada) y se puso un `<h1>` sin clase, perdiendo la alineación a la izquierda que el boceto sí mostraba — reportado explícitamente por el usuario como descuido de detalle.
- **Layouts de columnas/filas: usar `flex-grid`/`flex-grid-*`/`flex-grid-gap-*` (equivalente propio al `row` de Bootstrap, ver `tailwindcss/utilities/_flex.css` o el archivo equivalente del core), NUNCA `grid`/`grid-cols-*` de Tailwind, salvo que el layout sea genuinamente complejo (áreas nombradas, spans irregulares que `flex-grid` no puede expresar).** Preferencia explícita y repetida del usuario ELAN-SK — CAFEXPORT 2026-08-05: se corrigió `grid md:grid-cols-2 gap-8` a `flex-grid flex-grid-gap-8 md:flex-grid-2` en `banner-50-50`, tras habérselo señalado varias veces. Ojo: `flex-grid-*` no usa `gap-*` normal (rompe el wrap) — el espaciado va con `flex-grid-gap-*`/`flex-grid-gap-px-*`. Si una columna de `flex-grid-*` contiene un carrusel/slider u otro contenido con overflow propio, esa columna necesita `min-w-0` explícito (ver detalle en `wp-swiper-slider-builder` — sin esto el navegador puede clampear el ancho a un valor absurdo en vez de respetar el `flex-basis`).
- Repasar mentalmente `references/philosophy.md` antes de escribir clases.
- **Ante cualquier duda de cómo se marca un botón (u otro componente ya existente) en ESTE proyecto, nunca inventar el markup/las clases de memoria**: revisar primero la página de test real del proyecto (`test/test-buttons.php` en WordPress, o su equivalente por framework — buscar el archivo de test análogo generado en el paso 6/`references/test-page.md` si el nombre difiere) y copiar de ahí la estructura y clases reales ya en uso, **de forma literal**: el `class` del elemento va EXACTAMENTE como en el test (ej. `class="btn-tertiary"`), sin agregar utilidades propias encima (espaciado, color, lo que sea) salvo que el propio boceto/diseño lo pida explícitamente — cualquier clase extra "porque parecía necesaria" ya es inventar, aunque el nombre base esté bien copiado. Si el proyecto no tiene página de test o el componente no está ahí, buscar un uso real ya existente en el propio código (grep) antes de escribir algo nuevo por analogía genérica. Casos reales: CAFEXPORT 2026-07-29, se generó un botón/enlace "Leer Historia" con markup inventado en vez de revisar `test/test-buttons.php`; CAFEXPORT 2026-08-08, `cards/posts-slider-card.php` terminó con `class="btn-rtertiary mt-0"` — typo en el nombre base y un `mt-0` agregado que no estaba en el patrón de test (`class="btn-tertiary"` a secas).
- Si `impeccable` está instalado, repasar también sus reglas generales (sección "Design guidance" de su `SKILL.md`: color, tipografía, layout, motion, interacción, y la lista de bans absolutos) — cubren decisiones que `philosophy.md` no especifica.
- Preferir extender los patrones `@apply` existentes (`atoms/`, `components/`) antes que escribir utilidades sueltas repetidas.
- **Antes de crear un archivo `.css` NUEVO en `atoms/`/`components/`, confirmar que hace falta**: solo se justifica si (a) el patrón se va a **reusar en 2+ lugares** (otro template, otra card, otro componente), o (b) es genuinamente complejo aunque tenga un solo uso (muchos estados/breakpoints, tipo header/footer/form — secciones estructurales únicas del sitio). Si es poco código (un puñado de líneas de `@apply`) y lo consume un ÚNICO componente, **no crear un archivo nuevo** — aplicar las clases de Tailwind directamente en el markup (PHP/JSX) de ese componente, en vez de indirectar a un `.css` aparte. Menos archivos que saltar al depurar, y el HTML sigue siendo la fuente de verdad de un elemento que no se repite en ningún otro lado. Caso real CAFEXPORT, 2026-07-24: se creó `components/_stat.css` (`.stat` + 2 hijos, ~10 líneas) para una sección de cifras usada en un solo componente (`cards/impact-stats-card.php`) — no había reutilización real, solo el costo de un archivo extra sin beneficio.
- Si territorio nuevo pasa el filtro anterior (sí se reusa, o sí es genuinamente complejo), seguir el mismo patrón que `atoms/_buttons.css`: reset en `@layer base`, variante en `@layer components`, usando roles de color y tamaños ya existentes. Si además `impeccable` está instalado, correr `/impeccable critique <componente>` antes de darlo por terminado.
- **Orden de clases**: toda lista de clases Tailwind (nueva o al reorganizar una existente) sigue el orden fijo de bloques de `references/philosophy.md` §10 (semántica BEM → flujo/posición → layout → tamaños → bordes/forma/superficie → bg+texto fusionados → espacios → transiciones/animación/interacción → estados/group), con responsive pegado a su propiedad base y alfabético dentro de cada bloque.
  - Aplica SIEMPRE que se construya o modifique un archivo con clases Tailwind — no es una tarea aparte que hay que pedir explícitamente. Cubre TODO archivo tocado en un proyecto que use este core, sin importar el motivo del cambio ni si el pedido tiene algo que ver con diseño: un fix de bug, un cambio de copy/texto, agregar/quitar una sola clase, mover un bloque de PHP, lo que sea. Si al tocar una línea existente su lista de `class`/`className` queda desordenada (ya sea porque ya estaba mal o porque el cambio la desordenó), corregir el orden ahí mismo como parte del mismo edit, sin que el usuario tenga que pedirlo aparte.
  - **Automatización de editor**: no existe un formateador de terceros que aplique este orden en archivos con PHP interpolado (`prettier-plugin-tailwindcss` no soporta `.php` ni permite configurar un orden de bloques propio — confirmado 2026-07-23, ver `references/philosophy.md` §10 si hace falta reconfirmar la investigación). La solución real es un script propio: un sorter en Node (sin dependencias nuevas) que reordena `class="..."`/`className="..."` según estos mismos bloques, SALTEANDO por diseño cualquier atributo con `<?php`/`<?=` embebido (esos requieren juicio semántico — mover una variable PHP dentro de una lista de clases puede implicar reestructurar cómo se arma esa variable, ver el párrafo de "Clases armadas dinámicamente" en §10 — y no es seguro que un script los toque solo). Implementación de referencia ya construida y en uso en CAFEXPORT: `wp-content/themes/hello-elementor-depura/scripts/sort-tw-classes.js`, enganchado a `npm run build` (pasada única antes de compilar) y a `npm run dev` (modo `--watch`, reordena en cada guardado). Es portable: para instalarlo en otro proyecto con este core, copiar el script, ajustar `TARGET_DIRS`/`EXTENSIONS` a la estructura del proyecto, y agregar los mismos scripts de `package.json` (`sort-classes`, `sort-classes-watch`, más el hook en `build`/`dev`). Correr `--check` primero y revisar el diff antes de confiar en el modo de escritura en un proyecto nuevo — la tabla de clasificación de prefijos puede necesitar ajustes si el proyecto usa utilidades del core que CAFEXPORT no usa.

## Referencias

- `references/philosophy.md` — reglas condensadas, leer siempre primero.
- `references/color-mapping.md` — cómo mapear una paleta importada.
- `references/typography-clamp.md` — fórmula exacta de `clamp()` (dos variantes: proporcional y min/max explícito) para calcular tipografía responsive a mano si la calculadora no está disponible.
- `references/frameworks/wordpress.md` — instalación en WP (Vite + browser-sync + DDEV).
- `references/frameworks/js-frameworks.md` — instalación en React/Vite/Next/Tauri (dos variantes de core), fuentes con `next/font/google`, y preguntas para otros CMS.
- `references/frameworks/elementor.md` — duplicar colores/tipografía/botones al Design System nativo de Elementor (Variables + Global Classes) vía PHP directo, cuando el proyecto combina el core por código con edición libre en Elementor.
- `references/test-page.md` — cómo generar la prueba visual por framework.
- `assets/core/` — core unificado con plugins JS (contraste WCAG + botones/links contextuales), default para WordPress, React, Next.js, Vite y Tauri por igual.
- `assets/core-simple/` — core solo-CSS sin plugins JS, únicamente como fallback excepcional (ver `references/frameworks/js-frameworks.md`).
- `assets/core/readme.md` — documentación extensa original, consultar solo para casos borde no cubiertos en `philosophy.md`.
- `assets/wp-test-template/` — los 5 archivos PHP reales de referencia para la prueba visual en WordPress.
- `assets/react-next-test-template/` — plantilla real (page.jsx + componentes) para la prueba visual en React/Next, con copiado al portapapeles incluido.
- `assets/wp-header-example/` — header real de referencia, específico de WordPress (PHP desktop/mobile, `_header.css`, `menu.js`, modal de búsqueda en React, filtro de CTA por clase). Ver su `readme.md` para los 7 patrones reusables: layout `shrink-0`+`flex-1`+`ml-auto`, evitar `<a>` anidado con `the_custom_logo()`, acotar el `<img>` del logo, CTA por clase CSS en vez de "último ítem", hide-on-scroll sin togglear `position`, no dejar un módulo JS rehén de otro que falla, y depurar "no pasa nada al click" con el navegador real.
